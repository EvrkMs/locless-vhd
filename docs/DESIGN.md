# locless-vhd: развёртывание образов Windows с загрузкой клиентов из VHDX

Форк locless-disk. Разделы 1–14 унаследованы от него и описывают сервер, формат образа и
деплой физического диска. Новое направление проекта — Windows на клиенте из VHDX, раздел 15.

## 1. Цель

Самодостаточный сервер развёртывания образов Windows на ПК (компьютерный клуб).
Из FOG берём идею «хост → задача → агент», образы с блочным копированием
(только занятые блоки) и multicast. Убираем зависимость от Linux-компонентов
и неудобный интерфейс.

## 2. Принятые решения

| Тема | Решение |
|---|---|
| Клиенты | Только Windows. Среда агента: обычный WinPE (лицензия не нужна, по словам заказчика) |
| Загрузка | Только UEFI x64. Legacy BIOS не поддерживается и добавляться не будет: сервер не отвечает таким ПК, образы только GPT. Диск с MBR можно использовать как цель деплоя, он будет перезаписан в GPT |
| Идентификация хоста | По MAC-адресу. Все машины идентичны, различие только в MAC |
| Образ | Блочный, по принципу partclone: копируются только занятые кластеры |
| Multicast | Нужен с первого этапа (важная оптимизация) |
| Сервер | Один самодостаточный бинарник, работает на Linux и Windows Server |
| Язык | Go (сервер и агент): статический бинарник годится для WinPE, кросс-компиляция |
| Сборка | Через WSL-дистрибутив `claude` (см. глобальный CLAUDE.md), на хосте Windows ничего не ставим |
| Совместимость с CCBoot | Режим CCDisk (см. раздел 3) |
| DHCP | На первом этапе не трогаем: next-server и bootfile задаются вручную на MikroTik. proxyDHCP — позже, как опция |
| TFTP | Обязателен при любом варианте: UEFI получает загрузочный файл только по TFTP. Порт 69 на сервере CCBoot занят |
| Сосуществование с CCBoot | Не ломаем: службу не останавливаем, его адреса и порты не занимаем, `SO_REUSEADDR` и wildcard на 67/69/4011 не используем |

## 3. Контекст: CCBoot / CCDisk

По страницам ccboot.com (маркетинговые, детали могут быть неполными):

- CCDisk — режим CCBootCloud: Windows остаётся на **локальном SSD** каждого ПК,
  сервер отдаёт только общий игровой диск (отображается как обычная буква диска).
- Образ системы по сети не стримится. Нужны игровой диск и write-back диск, образ-диск не нужен.
- Кэширование (RAM + SSD) описано на стороне сервера. Клиентский блочный кэш в источнике не упомянут.
- При включении CCDisk CCBoot **останавливает** свои TFTP, DHCP и DHCP-proxy.
  *(На практике не подтвердилось: на сервере клуба CCBoot держит 67/69/4011 — см. §11.)*
  Следовательно, наш сервер может сам владеть PXE (DHCP/proxyDHCP, TFTP, HTTP).
  Одновременно с diskless-режимом на том же сервере наш PXE работать не сможет.
- Транспорт CCDisk в источнике не назван (iSCSI указан только для diskless-режима).

Наша задача: развёртывание и захват **системного диска**. Игровым диском занимается CCDisk.
В образ заранее ставится клиент CCDisk. Post-deploy агент на первом этапе не нужен.

## 4. Как устроен FOG (изучено, исходники в `reference/`)

- «Агент» FOG — это ~7000 строк bash (`fos`, `funcs.sh`) в мини-Linux, поверх partclone, udpcast, sfdisk.
- Опрос сервера: клиент каждые 5 с шлёт POST на PHP (`Pre_Stage1.php`, `mc_checkin.php`),
  пока не получит `##@GO` (так устроена очередь).
- Развёртывание: `udp-receiver | zstdmt -dc | partclone.restore -O /dev/sdXN`
  (одиночное: `cat` с NFS вместо `udp-receiver`).
- Захват: `partclone.ntfs -cs /dev/sdXN | zstd | файл на сервере`.
- Таблица разделов сохраняется отдельно (`sfdisk -d`) и пересчитывается под новый диск, в этом основная часть кода.
- Multicast: серверный демон запускает `udp-sender`, ждёт `--min-receivers` клиентов или `--max-wait`.
- Формат partclone: заголовок (версия, ФС, размер блока, число блоков) → bitmap занятых блоков →
  только занятые блоки с CRC. Структуры в `reference/partclone/src/partclone.h`.

## 5. Загрузка по MAC

1. ПК грузится по PXE (UEFI), получает iPXE от нашего сервера.
   UEFI умеет только TFTP, поэтому первый файл отдаёт TFTP-сервер; всё дальнейшее идёт по HTTP.
2. iPXE запрашивает скрипт: `GET /boot.ipxe?mac=...`.
3. Сервер ищет хост по MAC и проверяет, есть ли активная задача.
4. **Задача есть:** скрипт грузит WinPE через `wimboot`. На этапе iPXE подкладываются
   агент и файл запуска (идея заказчика), поэтому пересобирать `boot.wim` под каждое изменение агента не нужно.
5. **Задачи нет:** выход на локальный диск (Windows Boot Manager). Для UEFI это `exit` из iPXE.
6. **Неизвестный MAC:** тоже загрузка с диска. MAC попадает в список «обнаружены, не зарегистрированы»
   в интерфейсе, добавляется в один клик. Автоматически ничего не разворачивается.

Нужно проверить на практике: куда именно `wimboot` кладёт дополнительные файлы внутри WinPE
и как запустить агента (`startnet.cmd` или `winpeshl.ini`).

## 6. Технические идеи для Go-реализации

- **Bitmap занятых кластеров:** `FSCTL_GET_VOLUME_BITMAP` на `\\.\C:` (без разбора NTFS `$Bitmap`).
  Читаем только занятые кластеры, сжимаем zstd (pure Go, `klauspost/compress`), пишем свой формат.
- **Формат образа:** цепочка файлов. `.ldisk` — полная версия, `.ldelta` — только блоки, отличающиеся от родителя.
  Описание формата — в `proto/image.go`. Версии лежат в папке образа: `win11-club\v1.ldisk`, `v2.ldelta`, `v3.ldelta`.
  - Файл: заголовок → сжатые блоки → индекс (таблица разделов и список блоков) → концовка. Индекс в конце позволяет писать блоки
    потоком, а файл без концовки считается незаконченным захватом, поэтому оборванная запись не выглядит образом.
  - Блоки фиксированного размера (1 МиБ) привязаны к месту на разделе, поэтому изменение в одном месте не сдвигает остальные.
    Переменная нарезка, как в `casync`, не нужна: на диске данные не сдвигаются.
  - Блок определяется SHA-256 сырых данных. Свободные кластеры зануляются до подсчёта хеша, иначе мусор делал бы равные блоки разными.
    Поэтому bitmap в файле не хранится, он нужен только агенту при чтении. Пустой блок не хранится и не пишется при развёртывании.
  - Индекс каждого файла описывает весь диск и указывает, в каком файле цепочки лежит блок, поэтому чтение не обходит цепочку.
    По списку хешей захват отправляет только новые блоки, а развёртывание может скачать только отличия от диска клиента.
  - Блоки независимы: параллельное сжатие и естественные «слайсы» для multicast. CRC проверяет блок до распаковки, хеш — после.
  - Новая версия зависит только от индекса родителя, поэтому блок, исчезнувший и вернувшийся позже, записывается заново.
  - Удаление старой версии — слияние в новый `.ldisk`. Панель предупреждает, если цепочка длиннее 5 версий, а объединяет только по команде оператора.
  - Отказались: VHDX/AVHDX (нет сжатия и записи на Go, `qemu-img` не работает с дифференциальными дисками) и отдельные файлы блоков
    по хешам (десятки тысяч файлов, образ нельзя просто скопировать). Общих блоков между разными образами в этом формате нет.
    Отказ от VHDX касается только хранения на сервере. На клиенте образ живёт в VHDX, см. §15.
- **Разметка диска:** нативно, через `IOCTL_DISK_SET_DRIVE_LAYOUT_EX`; расширение/сжатие тома через
  `FSCTL_EXTEND_VOLUME` / `FSCTL_SHRINK_VOLUME`. Без sfdisk и ntfsresize.
- **Multicast:** собственный протокол по образцу udpcast (слайсы, NACK от получателей, повтор отправителем).
  `udpcast` под Windows не работает. Это самая рискованная часть. Unicast по HTTP (стриминг) делаем
  первым, чтобы отладить формат образа, затем multicast.
  Заменено 2026-11-13: мультикаст для деплоя отклонён, он нужен для фоновых обновлений ПК с
  VHDX, см. §15 «Обновления по мультикасту».
- **Экран агента:** графический, на чистом Go. `agent/ui` рисует кадр в память (шрифты Go с кириллицей встроены, от шрифтов WinPE не зависим),
  окно на весь экран выводит его через `SetDIBitsToDevice`. C#, .NET и WebView не используем: им нужен изменённый `boot.wim`.
  Экран только показывает состояние, управление идёт с сервера. Проверено в обычной Windows, в WinPE ещё нет.
- **`boot.wim`:** берём официальный из `sources\boot.wim` на ISO Windows, индекс 1 (Windows PE), без изменений. В git и релизы не кладём.
- **Подготовка к захвату:** как в FOG, удаление pagefile/hiberfil и очистка mounted devices.
- **Статус задач:** WebSocket или long-poll вместо опроса PHP. Очередь «ждёт слот» сохраняем.
- **Хранилище:** SQLite (pure Go, `modernc.org/sqlite`), образы в файловой системе сервера. Схема обновляется миграциями по `PRAGMA user_version`.
- **Связь агента с сервером:** HTTP и JSON на клиентском порту, типы в `proto/agent.go`. Адрес сервера, MAC и имя хоста агент берёт из
  `fogs-agent.json`, который сервер генерирует и подкладывает через `wimboot`, поэтому поиск сервера по broadcast на пути А не нужен.
  iPXE называет образ по концу пути URL, так что MAC передаётся в пути, а не в query.
  Отчёты привязаны к MAC и не защищены: подделать прогресс из сети можно. Для задач, меняющих диск, нужен токен на задачу.
- **Папка образов:** задаётся в настройках панели и хранится в базе. Не может быть внутри `EFI`, который отдаётся без авторизации.
- **Панель:** страница и JSON API в `server/web`, встроены в бинарник. Без входа, поэтому слушает только loopback, а другой адрес сервер отвергает.
  Доступ из сети клуба откроем вместе с авторизацией (вопрос 5 в §13). Ошибка базы при запросе клиента считается отказом: ПК грузится с диска.

## 7. Структура репозитория (предложение)

- `server/`: HTTP API, веб-интерфейс (`embed`), очередь задач, образы, multicast-отправитель, iPXE-скрипты, proxyDHCP/TFTP.
- `agent/`: бинарник `windows/amd64` для WinPE.
- `proto/`: формат образа и протокол multicast (общий пакет).
- `winpe/`: скрипты подготовки WinPE, iPXE и wimboot.

## 8. Модель данных (первый этап)

- **Host:** MAC (может быть несколько), имя, группа, привязанный образ.
- **Image:** путь, размер, формат, дата захвата.
- **Task:** тип (capture, deploy, multicast), хост или группа, статус и прогресс, времена.
- **Group:** набор хостов; multicast-сессия запускается по группе.

## 9. Разделы диска

- На клиенте будут все разделы, что были на эталоне.
- У каждого раздела в образе есть политика: `fixed` (размер как в образе) или `fill`
  (занять всё оставшееся место диска). По умолчанию `fill` получает самый большой NTFS-раздел
  (обычно C:), в интерфейсе можно переназначить.
- Задача захвата называется `clone`. Агент берёт первый GPT-диск с разделом EFI, для NTFS читает
  bitmap, остальное копирует целиком, шлёт хеши пачками и данные только новых блоков. Сервер пишет файл в `.incoming` и публикует версию
  после проверки. Оборванный клон начинается заново, продолжения пока нет.
- Цель: образ встаёт на любой диск, куда помещаются данные (диски от 128 ГБ, данных до 64 ГБ). Сжатие сделано через `diskpart shrink`, ему нужна служба
  дефрагментации: `defragsvc.dll` в `boot.wim` есть, но на реальном WinPE сжатие ещё не проверялось. Если том не сжался, он снимается как есть, а образу нужен диск не меньше тома.
- Диск для записи выбирает `chooseTarget`: сначала внутренний GPT-диск с разделом EFI; если такого нет — единственный внутренний диск или единственный пустой среди нескольких. В остальных случаях деплой останавливается. На диск без GPT (новый или с MBR) сначала пишется пустая GPT.
- Версии: откат (`restore`) только отключает версии после выбранной, файлы остаются (`image_versions.disabled`). «Вернуть» работает, пока отключённая версия продолжает цепочку; новый клон после отката идёт от выбранной версии, и старая ветка вернуть уже нельзя. Перед сменой цепочка проверяется по самим файлам (`NewChain`): родитель, сумма его индекса и список ID всех слоёв в индексе, поэтому номер слоя `File.Layer` не хранится отдельно. Слияние (`merge`) копирует сжатые блоки текущей цепочки в новый `.ldisk`, затем удаляет все старые файлы образа, включая отключённые.
- Очередь на образ: один клон на образ одновременно, деплоев сколько угодно. Деплой не ждёт клон и берёт последнюю законченную версию: принимаемый файл лежит в `.incoming` и не считается версией, пока не завершён. Второй клон ждёт ещё до сжатия тома (`/clone/claim`), сервер отвечает кодом 423, агент спрашивает раз в 10 секунд. Очередь держит только задача, дошедшая до агента, поэтому выключенный ПК с задачей никого не блокирует. Отмена задачи прерывает ожидание. Слияние заменяет файлы, поэтому на время слияния ждут и клон, и деплой.
- Задача `format` стирает диск и оставляет чистую GPT с одним томом NTFS и меткой `WB`, без EFI и MSR. Образ не нужен, диск выбирается как у деплоя, с теми же 20 секундами на отмену. Windows с такого диска не загрузится.
- Образ хранит полный путь к своей папке (`images.path`). Настройка «Папка образов» влияет только на новые образы.
- Отказоустойчивость: паника в службе, запросе или передаче TFTP ловится (`recovery`), пишется в лог со стеком, служба перезапускается. Лог сервера лежит в файле `-log`, то, что поймать нельзя, попадает в `<log>.crash`. Паника агента заканчивается экраном ошибки: том возвращается, стек уходит в лог сервера. Перезапуск самого процесса — задача установщика (служба Windows с `sc failure`).
- Задача записи называется `deploy`. Таблица строится под реальный диск (`Manifest.Fit`): `fill` занимает всё место, хвостовые разделы уходят в конец, том растягивается `extend filesystem`. Имя хоста пока не меняется. Агент пишет только на внутренний
  GPT-диск с разделом EFI: iSCSI, USB и VHD запрещены, диск без такой разметки не подходит. Перед записью 20 секунд предупреждения с отменой по Esc.
  Разделы блокируются и отключаются (`FSCTL_LOCK_VOLUME`, `FSCTL_DISMOUNT_VOLUME`), затем пишется таблица с GUID эталона: на них ссылается BCD.
  Данные пишутся через сам диск по абсолютному смещению: Windows помнит старый размер раздела с тем же началом и обрывает запись через раздел (`unexpected EOF`).
  Блок без записи в индексе — свободное место, его не пишем. Занятый блок из нулей хранится как запись с пустым хешем и обязателен к записи.
  Проверка на виртуальных дисках: `scripts/vhd-test.ps1`. После записи агент вызывает `bcdboot`, потому что запись Windows Boot Manager живёт
  в NVRAM платы и с образом не приезжает. Сбой `bcdboot` только попадает в журнал: данные уже на диске.
- Выход из iPXE без задачи настраивается в панели: `sanboot` (по умолчанию, ищет `bootmgfw.efi`, затем `BOOTX64.EFI`), `exit`, rEFInd. Как у `FOG_EFI_BOOT_EXIT_TYPE`.
- Образ создаётся в панели, а ПК привязывается к образу: `clone` и `deploy` берут образ из этой привязки.
- Захват повторяет порядок FOG (`fog.upload`, `shrinkPartition`), поэтому образ разворачивается и на диск меньше эталона:
  1. Сохранить исходную таблицу разделов: до первого изменения диска она уходит на сервер.
  2. Убрать pagefile и hiberfil, очистить mounted devices.
  3. Сжать файловую систему до минимума с запасом (у FOG не меньше 500 МБ). Сначала файловая система, потом запись раздела:
     обратный порядок отрезал бы данные. В FOG это `ntfsresize`, у нас `FSCTL_SHRINK_VOLUME` или `diskpart shrink`.
  4. Сохранить минимальную таблицу разделов. GUID диска и разделов не меняются: на них ссылается BCD.
  5. Прочитать блоки сжатых разделов.
  6. Вернуть исходную таблицу и расширить файловую систему: эталон снова как был. Шаг 6 выполняется и при ошибке на шагах 3–5.
- Том возвращается как в FOG (`saveOriginalPartitions`, `restoreOriginalPartitions`, `expandPartition`). До сжатия таблица уходит на сервер (`hosts.saved_table`), без этого диск не меняется. После снятия, ещё до итога задачи, агент записывает таблицу обратно и растягивает файловую систему (`Repair`, до 5 попыток), затем проверяет чтением диска. Если ПК выключился на середине, таблицу получит следующая задача этого ПК, кроме деплоя. Таблица другой разметки отвергается и удаляется. Образ при неудаче остаётся, задача завершается ошибкой, в панели видно «Том сжат».
- Раздел, который не удалось сжать, становится `fixed` и захватывается как есть, захват не прерывается (как в FOG).
- В манифесте нужны оба размера раздела: минимальный и исходный.
- Нужно проверить на практике: сколько даёт сжатие в WinPE (мешают неперемещаемые файлы) и какой размер `.ldelta` получается после него:
  сжатие переносит кластеры из конца тома, а блоки привязаны к месту на диске.
- При развёртывании таблицу разделов строим заново под размер диска: `fixed` сохраняют размер, `fill` получает остаток
  (минус хвостовые `fixed`, например Recovery). Раздел не двигаем, а размечаем с нуля, поэтому
  аналога `movePartition` из FOG не нужно. После записи блоков файловая система расширяется (`FSCTL_EXTEND_VOLUME`).
- Разделы и политики хранятся в индексе образа. Содержимое раздела: `blocks` (хранится) или `none` (MSR: только создаётся).
- Раздел EFI (FAT32) захватываем целиком посекторно: он маленький, а кластер 0 из `FSCTL_GET_VOLUME_BITMAP` на FAT, вероятно,
  начинается не со смещения 0 тома. C: и Recovery (NTFS) — по bitmap.

## 10. Sysprep и имя хоста

Sysprep (generalize) — штатная утилита Microsoft, которая обезличивает установленную Windows
перед клонированием: убирает SID, имя ПК, привязку драйверов, а при первой загрузке выполняет
донастройку по `unattend.xml`. Плюсы: чистые клоны, нужно для домена. Минусы: ограниченное число
rearm, сброс части настроек, может задеть клиент CCDisk.

Решение: на первом этапе клонируем как есть. Для различий по MAC агент в WinPE после записи образа
правит имя хоста **офлайн** (загрузка реестра `SYSTEM` развёрнутого раздела, `reg load`), так что
post-deploy агент не нужен. FOG делает то же самое (`changeHostname` в `funcs.sh`).
Вопрос: нужны ли разные имена хостов, или одинаковые допустимы?

## 11. DHCP и MikroTik

**Этап 1 (принято, сейчас):** DHCP остаётся у MikroTik. `next-server` и имя загрузочного файла
задаются там вручную для тестового ПК, наш сервер отдаёт только TFTP и HTTP. Ограничение: выдавать
их нужно строго per-lease (только тестовому ПК), иначе клиенты CCBoot уедут на нас; в RouterOS 7
это делается через option-set у lease.

**Этап 2 (опция):** свой proxyDHCP. DHCP выдаёт роутер MikroTik, его не трогаем. Наш сервер работает как **proxyDHCP**:
слушает DHCPDISCOVER с опцией 60 `PXEClient` (UDP 67 broadcast) и отвечает только PXE-данными
(next-server, имя загрузочного файла), а клиент подтверждает на порту 4011. Решение принимается по MAC.

**Требование для этапа 2: ничего не прописывать на роутере** (ни next-server, ни boot-file-name). Это должно работать
на любом роутере, в том числе без доступа к DHCP-опциям (например, провайдерский). Поэтому целевой режим один:
proxyDHCP. Условие: сервер в том же L2-сегменте, что и клиенты (или есть DHCP relay), и роутер не
фильтрует broadcast. Позже добавим полноценный DHCP как отдельный режим работы.
Этап 1 сознательно нарушает это требование: ручная настройка на MikroTik допустима, пока речь идёт
о тестовом ПК и чужие клиенты не затрагиваются.
Идея на потом: Wake-on-LAN с сервера для машин, у которых появилась задача.

**Реализация (`server/dhcp`):** этап 2 сделан раньше этапа 1, потому что разработка идёт на ПК, где порты 67/69/4011 свободны.
Сервер отвечает только MAC из явного списка, остальных пишет в лог: это заменяет per-lease ограничение из этапа 1.
Прошивке UEFI отдаётся `ipxe.efi` без опции 43 (она затем обращается на 4011), клиенту с user class `iPXE` — URL `boot.ipxe`.
Нужно проверить на практике: если в сети уже отвечает другой PXE-источник (`next-server` на MikroTik, proxyDHCP CCBoot),
какой ответ выберет прошивка тестового ПК.

Проверено на реальном ПК (2026-11-05): цепочка прошивка → `ipxe.efi` → `boot.ipxe` работает.
`ipxe.efi` сразу после старта запрашивает `autoexec.ipxe` по TFTP. Если файл есть, iPXE выполняет его вместо своего автозапуска,
поэтому сервер генерирует этот скрипт: он сам вызывает `dhcp` и переходит на `boot.ipxe`, а при ошибке выходит в UEFI.

## 12. Secure Boot (включён на клиентах)

Исходный iPXE и wimboot не подписаны ключом из базы `db` прошивки. Два пути:

**А. Свой CA, подписанные iPXE и wimboot.**
Мы собираем iPXE и wimboot сами и подписываем своим ключом. Сертификат (DER/`.cer`) один раз
добавляется в `db` каждого ПК вручную в UEFI. Идея агента, подкладываемого на этапе iPXE, сохраняется.
Плюс: быстрая HTTP-загрузка. Минус: ручное добавление сертификата на каждую машину, а сброс CMOS его стирает.

**Б. Цепочка, подписанная Microsoft.**
WinPE грузится штатным `bootmgfw.efi` + BCD + `boot.wim` по TFTP (как WDS). Регистрировать
сертификат не нужно. Минусы: агент должен быть в `boot.wim` (достаточно маленького загрузчика,
который докачивает основной агент по HTTP), загрузка `boot.wim` по TFTP медленнее (нужен windowsize),
и proxyDHCP отвечает **только** хостам с активной задачей, остальные грузятся с диска сразу.
Учесть: загрузчик в ADK должен быть подписан CA, которому доверяет `db` клиентов
(переход на Windows UEFI CA 2023).

Путь Б попробован и отвергнут: без iPXE ПК без задачи нельзя отправить на локальный диск, сервер может только молчать, и всё зависит от порядка загрузки в прошивке.

**Решение: официальная сборка iPXE 2.0.0 для Secure Boot.** Цепочка: `ipxe-shim.efi` (подписан Microsoft) → `ipxe.efi` из папки `x86_64-sb` → `wimboot` (подписан Microsoft). Свой CA не нужен, ручной установки сертификатов нет, shim работает и при выключенном Secure Boot. Загрузочный файл по умолчанию — `ipxe-shim.efi`. Путь А остаётся запасным, если упрёмся в ограничения подписанной сборки.

### Как клиент находит сервер с boot.wim (путь Б)

- proxyDHCP-ответ содержит `siaddr` (наш сервер), имя загрузочного файла (`bootmgfw.efi`)
  и опцию 252 с путём к BCD. Всё это приходит от нас, роутер не участвует.
- `bootmgfw.efi` берёт BCD с того же TFTP-сервера. В BCD путь к `boot.wim` задан как
  `[boot]\...\boot.wim`: `[boot]` означает «устройство, с которого загрузились», то есть наш сервер.
  IP в BCD не зашит, один BCD работает при любом адресе сервера.
- Скорость TFTP настраивается в BCD (`ramdisktftpblocksize`, `ramdisktftpwindowsize`).
- Агент в WinPE находит сервер сам: UDP broadcast «где сервер?» и ответ сервера. Адрес в `boot.wim`
  не зашивается. Это нужно проверить на практике.
- Файлы Microsoft (`bootmgfw.efi`, `boot.sdi`, `boot.wim`) в дистрибутив сервера не кладём.
  Скрипт сборки берёт их из ADK, установленного у пользователя.

Независимо от пути:
- Страница в интерфейсе для скачивания сертификата с **отображением SHA-256 отпечатка**
  (отпечаток сверяется вручную в UEFI, иначе подмена файла по незащищённому HTTP — это подмена корня доверия).
- Хранение CA: корневой ключ офлайн, подпись бинарников выполняется при сборке, а не на сервере в рантайме.
  На сервере лежит только публичный сертификат. Нужен план ротации и отзыва (`dbx`).
- Проверить, годится ли подписанный нами `wimboot` для `LoadImage` под Secure Boot.

## 15. Windows на клиенте из VHDX

### Идея

Подсмотрено у CCBoot: образ лежит на клиенте отдельным виртуальным диском, а записи уходят
в другой. У нас это встроенная загрузка Windows с VHDX (native VHD boot) и разностный диск:

- `base.vhdx` — ровно одна версия образа vN. Агент собирает его из цепочки `.ldisk`/`.ldelta`.
  Во время работы Windows он только читается.
- `diff.vhdx` — разностный диск поверх base. BCD загружает Windows с него, все записи сеанса
  идут сюда.

Сервер по-прежнему хранит и передаёт `.ldisk`/`.ldelta`: в них есть сжатие и версии.
VHDX — только формат на диске клиента.

Что это даёт:

- Сброс ПК: удалить diff и создать пустой. Своего драйвера не нужно, всё делает vhdmp из
  Windows. Альтернативы на уровне ФС хуже: свой minifilter требует подписи у Microsoft,
  а UWF есть только в Enterprise, Education и IoT.
- Дельта-клон без чтения всего диска: BAT разностного диска показывает, какие блоки
  менялись. При размере блока VHDX 1 МиБ он совпадает с нашим блоком.
- Известная версия на каждом ПК: base — это ровно vN, номер лежит рядом в файле состояния.
  Обновление до vM записывает в base только блоки, различающиеся между vN и vM. Это заодно
  решает вопрос «Версии после отката» из TODO.

### Разметка физического диска

Физический диск размечаем сами и всегда одинаково, разделы эталона не сохраняются:

- EFI (FAT32, около 260 МиБ): загрузчик, его кладёт `bcdboot`;
- MSR (16 МиБ);
- хранилище: NTFS на всё остальное, без буквы. На нём файлы виртуальных дисков и файл
  состояния.

Это делает задача `prepare` (кнопка «Подготовить диск под VHDX»): она всегда размечает диск заново. Деплой будет вызывать разметку сам, если хранилища нет (`proto.IsStoreLayout`); правильную
разметку он не трогает. Внутри виртуального диска своя GPT с одним разделом Windows,
EFI внутри не нужен.

Права на хранилище: владелец и полный доступ только у SYSTEM (от него работают загрузчик,
агент в WinPE и служба сброса `LoclessReset`), у администраторов только чтение, у остальных
пользователей ничего, наследование от корня закрыто. Деплой в VHDX выставляет их каждый раз.
Администратор может забрать владение обратно: это защита от игроков, а не от оператора.

Модель угроз: игроки работают под обычным пользователем без прав администратора. С правами
администратора схема не держится: он может подменить следующий diff, EFI и BCD, а проверка
изнутри Windows этого не поймает. Защита от администратора возможна только до старта Windows
(WinPE или BCD с сервера), это отложено.

### Учётные записи

В настройках панели задаются пароль администратора (общий для всех ПК, хранится на сервере как
есть, панель его не показывает) и имя пользователя для игроков. Деплой в VHDX:

- включает UAC в local: обычный пользователь при повышении прав получает запрос имени и пароля
  администратора на защищённом рабочем столе;
- если задано хоть что-то из учётных записей, кладёт `accounts.json` на хранилище; файл
  остаётся там, читать его могут только SYSTEM и администраторы.

Пользователи, пароли и группы лежат в кусте `SAM`, который меняет только запущенная Windows:
в WinPE их не поправить. Поэтому служба сброса при каждой загрузке, ещё до сброса diff,
включает встроенного администратора (ищет по RID 500, имя зависит от языка) и задаёт ему
пароль, убирает пользователя игроков из группы администраторов (группа по SID) или создаёт
его обычным пользователем без пароля, если в образе его нет. Изменения попадают в diff и
пропадают со сбросом, а на следующей загрузке применяются заново за доли секунды. Ошибка
пишется в `reset.log` и сброс не останавливает.

Служба и автовход Windows стартуют почти одновременно, поэтому пользователь игроков, который
в образе администратор, может успеть войти с этими правами в первые секунды. В образе его
стоит держать обычным пользователем, служба только подтверждает это.

Сначала было иначе: первая загрузка после деплоя шла прямо с `local.vhdx`, чтобы настроить
учётные записи один раз. Это не работает: поверх диска, с которого работает Windows, нельзя
создать разностный диск («файл занят другим процессом»), и ПК оставался на `local`.
Пароль идёт от сервера к агенту открытым текстом по HTTP в сети клуба.

### Что остаётся от прежнего деплоя и клона

- Сжатие данных остаётся: сервер хранит и передаёт `.ldisk`/`.ldelta` (zstd, хеши,
  версии). Деплой распаковывает блоки в base, клон сжимает их в `.ldelta`.
- Сжатие тома уходит: `diskpart shrink`, сохранение и возврат таблицы, `Repair`,
  `Manifest.Fit` и растягивание тома нужны были, чтобы образ влез на физический диск
  меньше эталона. Размер виртуального диска от физического не зависит.
- В клоне BAT разностного диска только подсказывает, какие блоки смотреть. Для них, как
  и сейчас, обнуляются свободные кластеры, считается хеш, и блок с тем же хешем, что у
  родителя, не отправляется.

### VHD и VHDX

Оба формата поддерживают разностные диски и загрузку Windows с них, поэтому в агенте один
интерфейс контейнера:

- создание, разностный диск, подключение, слияние — через virtdisk, общий код, отличается
  только тип хранилища;
- список изменённых блоков — свой парсер для каждого формата: у VHDX BAT и битмап секторов,
  блок 1 МиБ совпадает с нашим; у VHD BAT и битмап секторов в каждом блоке, блок обычно 2 МиБ.

Формат задаётся у образа и записывается в файл состояния. По умолчанию VHDX: у VHD предел
2 ТБ и только сектор 512 байт, а журнал метаданных VHDX переживает выключение посреди записи.

### Размер виртуального диска и место на хранилище

Размер VHDX задаётся у образа. По умолчанию это 0: агент берёт столько, сколько позволяет
хранилище конкретного ПК (`proto.AutoVHDSize`), так что на диске 240 ГБ Windows видит около
180 ГБ, а не 64. Блоки образа привязаны к месту внутри раздела, а растянутый том живёт в
local, поэтому разный размер на разных ПК не мешает ни дельтам, ни обновлению base.
Явный размер в панели остаётся для тех, кому нужен одинаковый.

Деплой выключает раздувание динамического диска до полного размера при загрузке
(`VirtualDiskExpandOnMount = 4` в `FsDepends` внутри local), поэтому файлы занимают только
записанное. Каждая запись Windows ложится либо на свободное место виртуального диска,
которого нет в base, либо поверх данных base, и только второе хранилище оплачивает дважды:

```
хранилище ≥ VHDX + max(VHDX / 10, 8 ГБ) + память ПК + 4 ГБ + 1 ГБ (local)
```

Десятая часть — запас на перезапись данных base за сеанс, память ПК — файл подкачки и дампы,
которые при загрузке с VHD лежат на хранилище. Если сеанс перепишет больше, кончится место на
хранилище, и Windows упадёт; сброс при следующей загрузке это вычистит. Раньше считали
худший случай, два полных VHDX, и на диске 240 ГБ выходило не больше ~100 ГБ.

Ограничения, которые надо учитывать:

- Загрузка с VHDX есть в Pro, Enterprise и Education, в Home нет.
- Нет гибернации и быстрого запуска, BitLocker внутри VHD не работает, крупные обновления
  Windows (feature updates) на VHD не ставятся.
- Динамический VHDX при загрузке раздувается до полного размера, если не выставить
  `VirtualDiskExpandOnMount` в `FsDepends` (деплой выставляет его в local).
- Base нельзя менять, пока поверх него есть diff: разностный диск станет недействительным.
  Base обновляется только из WinPE после удаления diff.
- Раздел с файлами VHDX виден из загруженной Windows, его надо прятать (без буквы).

### Цепочка на клиенте

Разностные диски называются `.vhdx`, а не `.avhdx`, как их называет Hyper-V: загрузчик Windows
определяет формат по расширению и читает всё, что не `.vhdx`, как старый VHD. С `.avhdx` загрузка
падала в `winload.efi` с ошибкой 0xc03a0001 (нет footer VHD). Деплой удаляет файлы со старыми
именами.

```
base.vhdx  ←  local.vhdx  ←  diff-a.vhdx / diff-b.vhdx
```

- base — блок в блок образ с сервера, одинаковый на всех ПК с этой версией. В него пишет только
  деплой (и в будущем обновление), больше ничего.
- local — то, что принадлежит этому ПК: растянутый том Windows, имя ПК, служба сброса. Деплой
  создаёт его заново. Если бы это писалось в base, обновление по дельте смешало бы блоки куста
  реестра `SYSTEM` от двух версий и испортило его.
- diff — сеанс игрока, создаётся поверх local и сбрасывается при каждой загрузке.

Отложено, может и не понадобиться: драйверы и настройки ПК в local и постоянный том для кешей
и дампов, на который ведут junction из образа.

### Обновление службы

Служба сброса — сам агент (`lvhd-reset.exe`), своего самообновления у неё нет. Новая версия
приходит, когда агент в WinPE пишет local или save: при деплое в VHDX, входе в Save Mode и
выходе из него, и задачей «Обновить службу». В обычном режиме задача пишет службу в local и
делает новый diff с загрузочной записью: diff поверх изменённого local недействителен. В Save
Mode служба пишется в `save.vhdx`, сверху у него ничего нет. Через Save Mode служба попадает
и в образ, но на ПК с VHDX её всегда перекрывает local.

### Место для сеанса

Сеанс игрока пишется в diff на хранилище. Когда место кончается, Windows падает, следующая
загрузка снова чистая, но игра потеряна. Поэтому служба сброса после сброса не завершается:
раз в 30 секунд она читает свободное место хранилища по пути тома (`\\?\Volume{GUID}\`,
буква не нужна) и показывает окно в сессии того, кто сидит за ПК (`WTSSendMessageW`: у службы
в сессии 0 нет своего рабочего стола). Меньше 5 ГБ — одно предупреждение «сохраните игру»,
меньше 2 ГБ — «сохраните и перезагрузите» раз в 5 минут. Предупреждение возвращается, только
когда свободно снова больше 6 ГБ. Окно закрывается само через 2 минуты. Игра в эксклюзивном
полноэкранном режиме может перекрыть окно. Там, где хранилища нет (образ развёрнут на
обычный диск), служба выходит сразу.

### Save Mode: изменения мастера в общий образ

Один ПК становится мастером образа: на нём ставят игры и обновления, переживающие
перезагрузку, а потом сохраняют их новой версией для всего клуба.

```
обычный режим:  base ← local ← diff-a / diff-b   (сброс на каждой загрузке)
Save Mode:      base ← save.vhdx                 (сброса нет)
```

- **Включить** (`savemode`, WinPE): `save.vhdx` поверх base, а не поверх local. Всё, что в
  local (растянутый том, имя, настройки этого ПК), в образ попасть не должно: блоки local
  поверх base — это NTFS, разорванная между двумя файлами. Base хранит том сжатым, как его
  снял клон, поэтому агент растягивает том внутри save. Туда же служба сброса, флаг
  `VirtualDiskExpandOnMount`, UAC и SafeBoot: они одинаковы для всех ПК, попадут в образ и
  безвредны, у каждого ПК local пишет их поверх. Служба читает файл состояния (`save`) и в
  этом режиме ничего не делает, учётные записи тоже не трогает. Загрузочная запись
  переключается на save до записи файла состояния, diff игроков удаляются последними.
- **Сохранить в образ** (`saveimage`, WinPE): обычный клон, только источник — подключённая
  цепочка base ← save, а не физический диск. Том сжимается, как в любом клоне (иначе образ
  не влезет на ПК с диском меньше), уходят только блоки, которых нет на сервере, версия
  полная, как после любого клона. Таблица разделов на сервер не сохраняется: это наш файл, и
  задача после сбоя не должна применить её к физическому диску. После успеха сервер сам
  ставит этому ПК «Развернуть в VHDX» новой версии: base мастера становится версией с
  сервера блок в блок тем же деплоем, что у всех. Пока деплой не прошёл, ПК остаётся в Save
  Mode со старым base, ничего не теряется.
- **Выйти без сохранения** (`savediscard`, WinPE): новый diff поверх прежнего local (base не
  менялся, local цел), загрузочная запись на него, затем `save.vhdx` удаляется.

Читаются только изменения. После сжатия тома агент отключает `save.vhdx`, читает его BAT
(`proto.ReadVHDXLayout`: заголовки, таблица регионов, метаданные, BAT по [MS-VHDX]; файл с
непроигранным журналом не принимается) и переводит блоки VHDX в места образа
(`ChangedPlaces`, размеры блоков и начало раздела любые). Затем клон начинается «поверх vK»,
где K — версия в файле состояния: сервер соглашается (`CloneInfo.Partial`), только если K —
последняя версия образа, и при закрытии отдаёт непрочитанным местам то, что у них в vK
(`Writer.Inherit`; места за концом сжатого тома отбрасываются). Если BAT не прочитался или
образ успел получить версию от другого ПК, читается весь диск, как в обычном клоне.
Парсер проверен на дочернем VHDX, созданном самой Windows (`proto/testdata`).

Свободные места внутри неизменённых блоков остаются как в vK, а не обнуляются, как в полном
клоне: для диска это свободное место, на содержимое тома не влияет. Деплой новой версии на
мастер по этапу 4 пишет только изменённые места, так что base мастера совпадает с сервером.

### Обновления по мультикасту

Решено 2026-11-13. Мультикаст возит обновления ПК, которые уже работают, деплой идёт по HTTP.
Деплою нужны все ПК в WinPE одновременно и ожидание отстающих. Работающие ПК слушают группу
весь день, так что пропуск обновления становится редким случаем, который закрывает HTTP.

1. Служба `LoclessReset` после сброса продолжает работать и держит с сервером постоянное
   соединение (WebSocket или HTTP long-poll), после обрыва переподключается через несколько
   секунд. Открытое соединение говорит серверу, что ПК включён. О новой версии сервер сообщает
   по нему сразу, и все ПК входят в группу одновременно: первый круг карусели покрывает почти
   всех. По тому же соединению служба шлёт прогресс приёма, а позже сервер будет передавать
   задачи. Опрос раз в минуту отклонён: ПК вступали бы в разное время, и сервер не знал бы,
   когда остановить карусель.
2. Нужные блоки служба считает сама: места, где хеш в списке новой версии отличается от
   `base.index`. Нулевым местам данные не нужны. Блоки опознаются по хешу.
3. Сервер крутит карусель: по кругу шлёт в группу блоки, новые в последней версии, с заданной
   скоростью. Ответов от ПК нет. Блок режется на куски размером с датаграмму (до 1400 байт),
   каждый кусок самостоятельный. Потерянный кусок ПК берёт на следующем круге, ПК, включённый
   позже, ждёт следующего круга.
4. Служба складывает принятые блоки в `update.part` на хранилище, сжатыми, как они хранятся на
   сервере, и проверяет CRC и хеш каждого. После двух кругов недостающие блоки она докачивает по
   HTTP. Так же докачивает ПК, отставший на несколько версий: в карусели только блоки последней.
5. Когда всё собрано, служба сообщает серверу. Сервер ставит ПК задачу «Применить обновление».
   На следующей перезагрузке агент в WinPE пишет блоки из `update.part` в base так же, как
   деплой по дельте, и пересоздаёт local и diff. Если файл неполный или base не та версия, идёт
   обычный деплой в VHDX по дельте с сервера.

Нужно в сети: IGMP snooping на коммутаторе (MikroTik), иначе группа идёт на все порты, включая
точки Wi-Fi. Служба сама добавляет правило брандмауэра Windows на свой UDP-порт. Скорость
карусели задаётся в панели, приём идёт с низким приоритетом, чтобы не мешать игре.

### Закрытые вопросы

Что уже рассматривали и отклонили или выяснили. Не предлагать заново без новых данных.
Записано 2026-11-13.

| Вопрос | Решение | Почему |
|---|---|---|
| Разностные диски `.avhdx` | нет, `.vhdx` | загрузчик читает не-`.vhdx` как VHD: 0xc03a0001 в winload |
| Загружать local один раз, чтобы применить учётные записи | нет, учётные записи на каждой загрузке | из Windows, загруженной с local, нельзя создать diff поверх local: файл занят |
| Отказаться от local, чтобы обновлять base | нет, local пересоздаётся при каждом обновлении base | дочерний диск привязан к байтам родителя: NTFS в local развалится; PnP после обновления доустановится один раз |
| Свой блочно-файловый формат диска | нет | фильтр-драйвер, подпись, Secure Boot — месяцы работы ради того, что даёт пересоздание local |
| Правка реестра из iPXE | невозможно | iPXE не понимает NTFS и не пишет на диск; настройки на каждую загрузку делает служба сброса, разовые — агент в WinPE |
| Linux вместо WinPE | нет | вторая среда под Secure Boot; `qemu-nbd`, по-видимому, не открывает дочерние VHDX (не проверяли) |
| WinPE: `boot.wim` с ISO или WinRE сервера | WinRE, урезанный `build.ps1` | не нужно копировать с ISO; 738 → 505 МБ против 625 МБ у ISO (Server 2025, 26100) |
| Урезать WinPE через `dism /Remove-Package` | нет, удаление файлов | DISM на Server 2025 не обслуживает пакеты WinPE: ошибка 87 и для WinRE, и для boot.wim |
| Переименовать diff в `*.diff.vhdx` | нет | хранилище без буквы, пользователь файлы не видит |
| Безопасный режим | служба сброса прописана в `SafeBoot\Minimal` и `\Network` | иначе сеанс безопасного режима переходил в следующую загрузку |
| Save Mode поверх local | нет, поверх base | без local в образ уходит не всё, что видела Windows (NTFS разорвана); с local — настройки одного ПК |
| Save Mode: слить save в base мастера (MergeVirtualDisk) | нет, деплой новой версии | клон обнуляет свободные кластеры, base мастера разошёлся бы с сервером |
| Save Mode: не сжимать том при сохранении | нет, сжимать | растянутый под мастера том не влезет на ПК с диском меньше |
| Деплой по мультикасту | нет, мультикаст только для обновлений | все ПК должны одновременно ждать в WinPE, отстающие держат всех |
| Слой baseV2 под старым local, слияние без WinPE | нет, `update.part` и запись из WinPE | local описывает NTFS старой версии; новый local онлайн не собрать из-за GUID диска |
| A/B base, как у CCBoot | нет, один слитый base | две полные копии системы на диске; local для второй цепочки упирается в тот же GUID |
| Скачивать образ файлом на диск ПК и разворачивать с него | нет, блоки по HTTP | двойная запись на SSD, нет дельты, нужен временный раздел |
| Первым в BIOS диск, а не сеть | нет, сеть первой | задачи (подготовка диска, клон, деплой на пустой диск) идут только через PXE |
| После WinPE грузиться сразу с диска (UEFI `BootNext`) | нет, каждая загрузка через iPXE | задачу могут добавить в любой момент, ПК должен каждый раз спросить сервер |

### План

0. Форк: отдельный репозиторий, модуль `locless-vhd`. Сделано.
1. Ручной прототип, без кода, на ВМ и затем на PC02: VHDX с блоком 1 МиБ, образ в нём,
   `bcdboot`, разностный диск, загрузка с него. Проверить редакцию Windows, античиты, CCDisk,
   скорость (`-dev` и CrystalDiskMark), удаление и пересоздание diff, `VirtualDiskExpandOnMount`,
   какой путь пропишет `bcdboot` при подключённой цепочке. Если античиты или CCDisk не
   работают, дальше не идём.
2. Задача `prepare`: EFI, MSR и хранилище NTFS без буквы. На нём `base.vhdx`,
   `diff-a.vhdx` / `diff-b.vhdx` (или `.vhd`) и файл состояния (образ, версия, формат,
   хеш индекса). Проверка места по формуле выше.
3. Деплой в VHDX: агент создаёт VHDX через virtdisk (`CreateVirtualDisk`, блок 1 МиБ),
   подключает его и прогоняет существующий деплой на подключённый диск (VHD-цель разрешается
   только в этом режиме). Затем создаёт diff, выполняет `bcdboot` и пишет файл состояния.
   Работает на ПК клуба. Задача `deployvhd` (кнопка «Развернуть в VHDX»), размер VHDX —
   настройка образа, по умолчанию по месту на хранилище. Внутри VHDX весь диск образа (EFI, MSR, C:,
   Recovery), поэтому деплой и клон работают с подключённым VHDX как с обычным диском. Растянутый
   том, имя ПК и служба сброса пишутся в local, чтобы base совпадал с сервером, а сброс diff
   их не терял. Проверить в WinPE: раскладку структур virtdisk,
   допускает ли разностный VHDX блок 1 МиБ, какой путь пропишет `bcdboot` с подключённого diff,
   форматирует ли diskpart хранилище с атрибутом «без буквы».
   Перед `bcdboot` деплой форматирует раздел EFI: на диске с готовым хранилищем разделы не
   пересоздаются, а `bcdboot` дописывает в найденный BCD, и в меню загрузки оставались записи
   прошлых деплоев на удалённые файлы.
4. Обновление версии. Сделано иначе, чем задумывалось: считает агент, а не сервер. После
   полного деплоя агент кладёт на хранилище `base.index`: образ, версию, размер блока, таблицу
   после `Fit` и хеш каждого записанного места. Следующий «Развернуть в VHDX» того же образа
   сравнивает с ним список деплоя новой версии и пишет в существующий base только места с
   другим хешем (свободные в новой версии не трогает, как и полный деплой); local, diff и save
   создаются заново. Старая версия на сервере не нужна: её могли удалить или слить.
   Полный деплой — если нет `base.index`, другой образ или размер блока, или таблица новой
   версии на этом VHDX ложится иначе (`proto.SameLayout`; размер сжатого клоном тома не
   мешает, `Fit` всё равно растягивает его). `base.index` удаляется до первой записи, так что
   оборванное обновление сменяется полным деплоем. Написано, на железе не проверено.
5. Сброс при загрузке: служба `LoclessReset` в base. Это сам агент (`lvhd-reset.exe -reset`
   в `System32`), деплой в VHDX ставит его в local через реестр офлайн. При старте Windows служба
   находит хранилище по метке, временно даёт ему букву, удаляет второй diff пары (A/B), создаёт
   его заново поверх local, переключает `{current}` в BCD (`device` и `osdevice`) на него и пишет
   файл состояния. Запись сеанса уходит в diff, с которого Windows загрузилась, а следующая
   загрузка идёт с чистого. Запись BCD меняется только после готового diff, поэтому сбой или
   выключение оставляют загрузку как была. Если файл состояния отстал от BCD, служба видит, что
   «второй» diff занят, и меняет их местами. Журнал — `reset.log` на хранилище. Написано, на
   железе не проверено: создание второго потомка у base, который держит загруженная Windows, и
   `bcdedit` с буквой хранилища.
6. Изменения в образ: сделано как Save Mode (раздел выше). Клон цепочки base ← save читает
   только блоки, которые есть в BAT `save.vhdx`, остальное сервер наследует от версии в base;
   затем деплой новой версии, который по этапу 4 пишет только изменения. Написано, на железе
   не проверено.
7. Панель и сервер: режим ПК (диск или VHDX), версия в base, время последнего сброса,
   предупреждение о версии, отключённой откатом. Есть очередь задач и признак Save Mode.

Состояние на 2026-11-13: этапы 2, 3 и 5 работают на ПК клуба (ошибки загрузки 0xc03a0001,
0xc000000f и раздувание VHDX исправлены по ходу), этап 1 отдельно не делали. Этап 4 и Save
Mode написаны, на железе не проверены.
